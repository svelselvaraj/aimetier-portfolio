AImetier

A multi-agent operating platform for teams of AI agents.

I built AImetier as an alternative to Grok Bot and ChatGPT dots for work that takes a team of agents. Agents proactively pick up tasks, collaborate with specialists, and recall lessons from earlier runs. The orchestration layer coordinates handoffs, while the runtime harness gives each agent the context, memory, and tools it needs. Guardrails enforce access permissions, reviewers check results against evidence, and the workflow pauses for human approval when required.

System design

Inside an AImetier instance

Instance components

Read the component map

The workspace portal and operator console reach the web API through the HTTPS gateway. PostgreSQL stores tasks and notifies the leader worker. Object storage holds files and session state. The worker dispatches tasks to the runner controller, which provisions the isolated agent runner and its adapter. Model calls go through the AI gateway to an LLM provider. Connected tool calls go through the MCP proxy for permission checks. Browser actions go through the browser broker to an isolated session. The egress proxy checks the destination before the browser reaches a website.

Autonomous run · A scheduled data-quality brief

Read the run trace

A schedule wakes the assigned agent. The worker loads permitted context and the budget. The runner prepares the brief using its configured tools. The server verifies the checks for this run. Work can return for revision, finish under policy, or wait for operator approval. Usage and the review decision remain attached to the run.

Team workspace

How the agent team is organised

AImetier brings the structure of a company to a team of AI agents. Each agent has a role, can call on a specialist, and can pass finished work to a reviewer. People step in when a decision needs their approval.

Multi-agent orchestration

How the platform works

Isolated execution
The worker schedules the task. A separate controller provisions an isolated runner with a scoped workspace and approved tools. Tenant-level database policies also apply when agents retrieve data.
Short-term context
The active thread carries the conversation and task inputs across turns. The platform assembles the run context from the agent’s instructions, permitted sources and tools. Temporary chat excludes prior conversations.
Long-term memory
Agents can save a lesson after a run. PostgreSQL and pgvector retrieve relevant lessons on later tasks. New memories are private to the agent by default. Sharing a lesson with a department or company requires an explicit promotion.
Guardrails along the run
The portal authenticates the caller and scopes access to their workspace. During execution, the runtime treats retrieved content as untrusted data and restricts the agent to approved tools in an isolated workspace. The server keeps the task open until the required checks for that run pass.
Prompt injection guardrails
A retrieved document can contain text that reads like a command. The runtime marks that text as source material, labels instructions by origin and uses the model’s system channel where available. The server independently enforces tool permissions, so text inside a document cannot grant access.
Grounding and hallucination checks
For a weekly quality brief, the analyst can retrieve the underlying validation results and a reviewer can reconcile the draft’s claims against them. For run-bound tasks, the server computes whether the assigned checks passed from their recorded results. A confident summary alone cannot mark the work complete.
LLM-as-judge evaluation
In the evaluation suite, deterministic checks screen out structurally invalid results. An LLM judge grades the remaining outputs against a rubric. Regression tests compare scores by role and work category, so a drop in reviewer quality stays visible.
Peer review and human approval
The reviewer checks the work and can accept it, return it for revision or escalate a decision. The platform uses that verdict and the approval policy for the action to decide when a person needs to step in. High-impact actions and unresolved concerns can pause the run for human review.
Run observability
The Operations Center shows agent activity, run health and tool connections. Operators can follow a run from startup through tool calls, validation and the reviewer’s decision. OpenTelemetry exports operational metrics to configured dashboards, where operators can check whether a slowdown affected one run or the wider instance.
Monitoring agent
The team’s monitoring agent, the Coach, compares the assignment with the recorded actions, the reasons the agent gave for its decisions and the work it delivered. Its report identifies which steps advanced the task, where the evidence is unclear and what remains unfinished. A report might trace repeated file searches to missing workspace instructions and propose the specific guidance the next run needs.
Adapter-agnostic and model-agnostic orchestration
The agent adapter lets the same workflow run across runtimes such as Claude Code, Codex, Gemini and Hermes. For inference, a workspace can use any LLM available through a compatible provider or adapter. Teams choose their models and fallback order without rewriting task handoffs or review steps.
Cloud-agnostic deployment
The platform has infrastructure definitions for AWS, Azure and Google Cloud. AWS is the documented reference deployment, Azure includes an AKS deployment path, and the Google Cloud configuration is validated in CI.
